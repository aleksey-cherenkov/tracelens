and the get_slice filter for message_type=sms returned exactly 8 matching journeys — i.e. the fragmentation 
and the sms channel line up.

ruled out:
  - A recent deploy to comms-ingest (sha a91f2c4) or comms-orchestrator (sha 7d3b8e1) caused the trace to stop
after two services.
    Both deploys are recorded as occurring 1474 and 2734 minutes after the earliest journey in this slice, 
i.e. after journeys with the same fragmentation pattern were already produced. A deploy that postdates the 
first affected record cannot be its cause.
  - comms-sender is failing outright for SMS messages, so nothing runs past comms-orchestrator.
    The correlation_id-joined timeline for corr-0003/corr-0007/corr-0013 shows comms-sender records ('consume 
{message_type}-queue' and 'send {message_type}') present and completing after the point where trace_id changes
— the work is recorded, just under a different trace identifier.

limits the answer worked under:
  - `trace_id` reaches only part of the path for these journeys -- any trace-keyed view shows a fragment with 
no indication it's incomplete
  - `status` and `http.status_code` are constant and carry no health signal, so nothing here confirms success 
or failure of the sender step beyond structural presence of records
  - 86% of records carry no correlation_id and cannot be tied to a specific journey, so this cannot be 
generalized beyond the 8 sms journeys actually inspected
  - no error signal exists anywhere in this window, so 'it failed' and 'it succeeded but wasn't linked' look 
identical

limits it did not address:
  - `http.status_code` is constant at 202 across all 41 records, so it cannot distinguish anything and no 
alert built on it can ever fire
  - `status` is constant at 'OK' across all 273 records, so it cannot distinguish anything and no alert built 
on it can ever fire
  - in particular, a healthy-looking `status` is not evidence that anything worked -- the field would read the
same if everything failed
  - no finding here can be based on an error signal, because there is none -- everything must be inferred from
structure, absence and timing instead
  - any existing alerting built on error status or log level is blind in this window by construction
  - 86% of this data can never support a claim about a specific journey -- only about volume
  - any search starting from an identifier misses those records entirely, however relevant they are

would resolve the remaining ambiguity:
  - the comms-sender code at the point of consuming {message_type}-queue for sms, specifically whether it 
starts a new trace context instead of continuing the inbound one
  - confirmation of which identifier (trace_id vs correlation_id) the trace viewer the user is looking at 
actually keys on
  - whether the same fragmentation occurs for push (also via AWS Pinpoint, same queue-consume pattern) versus 
email (SendGrid), to see if this is Pinpoint-specific or sms-specific
